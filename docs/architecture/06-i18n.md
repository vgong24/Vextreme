# Internationalization (i18n)

## The localization constraint

**No display string is hardcoded anywhere in this codebase.**

This applies to:
- Build scripts (`.js` files in `lib/`)
- Browser JS (`vextreme-index-v2.js`, `arc-nav.js`)
- HTML templates inside build scripts
- Arc labels, navigation chrome, button text, status messages — everything

If you are writing a string a human will read, it belongs in
`data/strings/source/`. Not inline. Not as a JS variable. Not as a
template literal. In the source file, keyed, compiled, and referenced
by key.

**Violations to recognize:**
```js
// WRONG — hardcoded display string
html += 'You Are Here: ' + title;
html += '← prev';
const label = ARC_LABELS[arcName];  // ARC_LABELS table in JS

// RIGHT — key referenced, text comes from compiled bundle
html += t('common.nav.you-are-here') + ': ' + title;
html += t('common.nav.prev');
const label = strings['arcs.' + arcName + '.heading.title'].text;
```

## Element key as canonical anchor

The key name (`common.label.page-live`) is the system's identifier for that UI
element. Its value is an extensible object — new systems attach their own
namespace without breaking existing readers:

```json
"common.label.page-live": {
  "strings": {
    "en": { "text": "Page live" },
    "ja": { "text": "公開済み" }
  }
}
```

Future namespaces extend the same object:
```json
"common.label.page-live": {
  "strings":     { "en": { "text": "Page live" }, "ja": { "text": "公開済み" } },
  "testId":      "label-page-live",
  "dataKey":     "PAGE_LIVE",
  "designToken": "label.page-live"
}
```

Each consuming system reads only its own namespace. The key registry in
`data/strings/source/` is not just a string file — it is the **element
identity layer** for the entire UI.

---

## Key convention

`{scope}.{element-type}.{semantic-name}`

| Segment | Purpose | Examples |
|---|---|---|
| `scope` | Where this element lives | `common`, `archives`, `liberation`, `claude-answers-the-doubt` |
| `element-type` | What kind of element it is | `label`, `button`, `heading`, `nav`, `status` |
| `semantic-name` | What it means, in kebab-case | `page-live`, `copy-filename`, `overall-progress` |

---

## Scope placement — where does a string belong?

Ask these questions in order:

**1. Does it appear on 3 or more pages/surfaces?**
→ `common.{element-type}.{semantic-name}` in `source/common.json`

**2. Is it specific to one arc, shared across that arc's pages?**
→ `{arc-key}.common.{element-type}.{semantic-name}` in `source/arcs.json`
   or a dedicated `source/{arc-key}.json`

**3. Is it specific to one page only?**
→ `{slug}.{element-type}.{semantic-name}` in `source/pages/{slug}.json`

**4. Is it a generated page's chrome (build-health.html, index.html)?**
→ Scope is the page name: `build-health.{element-type}.{semantic-name}` in
   `source/archives.json`

**The `common` scope is semantic, not just organizational.** It signals
"this element is intentionally shared." Using `common` for a string that
only appears in one place is a false signal — scope it to where it lives.

## Delivery mechanism by context

**Build scripts generating static HTML** (build-health.html, index.html):
- Read `data/strings/compiled/strings.en.json` at build time
- Call `t(key)` in the template — text is baked into the output HTML
- No runtime resolver; no string JSON embedded in the page

**Browser JS** (vextreme-index-v2.js, arc-nav.js):
- String constants needed at runtime are injected as build-time constants
  where possible (e.g. `var COPY_LABEL = "Copy filename"` baked by build script)
- For browser-only libraries not run through a build script, load the
  compiled EN bundle and expose a `t(key)` helper — do not embed all languages


## Effective-language authority across nested surfaces

The selected locale is one same-origin state, not one preference per FAB instance.

```text
explicit shared URL ?lang=  -> initial override when supported
localStorage["vex-lang"]    -> persisted same-origin selected language
vextreme:languagechange     -> same-document notification after convergence
storage("vex-lang")         -> parent/iframe/sibling browsing-context synchronization
```

`widgets/fab-lang.js` owns this runtime contract for both God-Script pages and
the shell-era auto-loader. A language change updates the FAB's visible state,
the current document URL, `<html lang>`, translated `data-i18n` text, and
the persisted `vex-lang` value. Other same-origin browsing contexts consume
the storage event and apply the same language; local consumers such as Terrain
listen to `vextreme:languagechange`. This keeps an embedded reader and its
parent FAB from becoming independent language stores.

Partial translation fallback is deterministic: each page captures its authored
English/source text before the first swap. Switching from one non-English
language to another may never leave text from the previous locale behind;
missing target-locale keys restore EN/source text.

Terrain screenshot evidence already has locale identity. Its preview/read side
therefore follows the same effective selected language when a matching capture
exists and falls back to EN (then another available capture) only when that
locale has no evidence. Embedded reader URLs also carry the effective
`?lang=` so first load and share/open-standalone behavior agree with the
persisted preference.

**Ordering rule for visual evidence:** populate and compile the intended
translations first, then capture screenshots for those locales. A successful
FAB selection by itself is not proof that a page has translated strings; do
not label an English fallback render as localized screenshot evidence merely
because `vex-lang` was set.

Language **availability** is now page-aware without becoming a second selected-language
authority. `lib/build-index.js` combines each page's declared viewmodel scopes
with `data/strings/compiled/scopes/index.json` and emits
`data/index.json.pageLanguageMap[slug]`:

- `availableLangs` = EN plus target locales that have at least one translated key
  in one of that page's declared content scopes. Translation of `common` UI alone
  does not make an unrelated page advertise a locale.
- `completeLangs` = EN plus target locales whose every runtime-required scope
  (`common` + that page's declared scopes) has the same key count as EN.

The user-facing FAB consumes `availableLangs`, so useful partial translations
remain reachable and missing keys still fall back deterministically to EN/source.
Localized screenshot automation consumes the stricter `completeLangs`; a partial
page may never be filed as fully localized evidence merely because the FAB can
select that locale. `data/index.json.supportedLangs` remains the site-wide
aggregate and backwards-compatibility fallback, not the default page truth.

### Page × locale screenshot matrix

`scripts/screenshot-page.js` remains the focused one-page review tool, but its
browser/server/verified-locale capture path is also reusable. The site-scale
orchestrator is `scripts/screenshot-localization-matrix.js`:

```bash
# inspect the exact eligible cells; no browser and no writes
npm run localization:screenshots -- --dry-run

# optionally narrow the proof
npm run localization:screenshots -- --dry-run --slug specimen-full-translation --locale ja

# capture all currently complete cells into the explicit Assets checkout
npm run localization:screenshots -- --assets-root ../Vextreme-Assets
```

Matrix formation is deterministic:

```text
real pages/*.html
  INTERSECT
data/index.json.pageLanguageMap[slug].completeLangs
  -> [{ page, locale }, ...]
```

A real matrix run requires an explicitly supplied Vextreme-Assets checkout. It
starts one Chromium process for the crawl, gives every cell a fresh browser
context, serves the branch-local repository, and behaviorally verifies every
non-EN locale through the current FAB before capture. PNGs live only in OS temp
storage during the crawl. Each successful cell is immediately handed to
`Vextreme-Assets/scripts/ingest-screenshot-evidence.mjs`, preserving the
existing canonical coordinate:

```text
evidence/screenshots/vextreme/{slug}/{locale}/default/1280/{sha256}.png
```

The Assets record remains bound to the exact Vextreme commit and
`pages/{slug}.html`; the matrix runner does not own or duplicate that schema.
After the crawl it runs the Assets manifest check and removes its temporary PNGs.
This makes screenshot scale a consequence of translation completeness: as
hash-bound translations are accepted and a page's `completeLangs` grows, the
next matrix run automatically gains the new page/locale cells.

## Pipeline

```
data/strings/source/          — scoped source files (write side; edit these)
  common.json                 — globally reusable UI strings
  arcs.json                   — arc title strings (16 arcs; display authority)
  archives.json               — build-health.html-specific strings
  pages/{slug}.json           — per-page strings (created as pages are ported)

lib/strings-check.js          — integrity pass (run before compile)
lib/strings-compile.js        — merges source → compiled bundles + manifest
lib/strings-export.js         — exports per-scope CSVs for translators
lib/strings-import.js         — merges completed CSVs back into source

data/strings/compiled/        — generated bundles (committed as artifacts)
  strings.en.json             — EN bundle: { key → { text, aria-label } }
  strings.ja.json             — JA bundle: same shape
  manifest.json               — { key → { enHash, langs } } for stale detection
  scopes/{scope}.{lang}.json  — same shape, one scope's keys only (see below)
  scopes/index.json           — { scope → { lang → keyCount } }, discovery without fetching every file

lib/build-index.js             — derives pageLanguageMap from page scopes + scope counts
data/index.json                — pageLanguageMap[slug].availableLangs / completeLangs

data/strings/migrations.json  — append-only key rename log (never delete entries)
data/strings/batches/export/  — CSV batches sent to translators
data/strings/batches/import/  — completed CSV batches waiting to be imported
data/strings/orphans.json     — quarantined keys with no migration
```

## Scaling past one bundle

The flat `strings.{lang}.json` bundle merges every source file's keys into one
file, regardless of scope. At today's size (a few pages, ~125 keys) that's
fine and stays the default. It stops being fine well before a site reaches
anything like a thousand pages: every page would fetch and parse the entire
project's strings on every load, one merge-conflict-prone file would gate
every string edit regardless of which page it belongs to, and there would be
no natural place for a staged translation or an A/B copy variant to live
without touching the file every other page also depends on.

`lib/strings-compile.js` also writes `data/strings/compiled/scopes/{scope}.{lang}.json`
— one bundle per source file's `_meta.scope`, same shape as the flat bundle.
This is **additive, not a replacement**: nothing currently fetches these, and
the flat bundle keeps being generated and keeps working exactly as before.

A page opts in by declaring its scopes before `widgets/lang-fab.js` loads:

```html
<script>window.VEX_STRING_SCOPES = ['demo'];</script>
<script src=".../widgets/lang-fab.js"></script>
```

`lang-fab.js` then fetches only `common` + the declared scopes (in parallel,
merged client-side) instead of the flat bundle. A page that doesn't set
`window.VEX_STRING_SCOPES` is unaffected — the legacy fetch path is still the
default and isn't going away.

**Variants** (A/B copy tests, staged translations not yet promoted to
production): a source file with `_meta.variant` set (e.g. `"variant": "b"`)
compiles to `scopes/{scope}.variant-{variant}.{lang}.json` — a sibling of the
base scope bundle, not a merge into it. A page requests one via
`window.VEX_STRING_VARIANT = 'b'`; `lang-fab.js` falls back to the base scope
bundle for any scope that doesn't have that variant compiled, so a partial
variant rollout (only some scopes overridden) degrades safely rather than
breaking.

→ *When a scope grows large enough that even its own bundle feels heavy
(imagine a single page with hundreds of strings), the same `_meta.scope`
mechanism supports splitting further — nothing about this requires a scope
to map 1:1 with a page.*

## Arc-chunked bundling pilot (Session 025, resolving od-001/td-006)

Session 013 flagged a real question before the site ever added a third
language: the per-scope-combo model above issues one parallel fetch per
scope on every language switch. At 2 languages and a few dozen nodes that's
fine. td-006 named the ceiling explicitly and set a hard gate: **decision
must be made before adding a third language; do not design the third
language's pipeline on the current per-scope-combo model.**

Session 025 needed a real third language (`zh`, for a bilingual engineering
dossier) and resolved the question with a **scoped pilot**, not a full
migration:

- `data/arcs-v2.json` supports an opt-in `"bundlingStrategy": "arc-chunked"`
  field per arc. Arcs that don't set it are completely unaffected — the
  per-scope-combo path above keeps being the default for the other 16 arcs.
- `lib/build-arc-bundles.js` (new) writes one
  `data/strings/compiled/arcs/{arcId}.{lang}.json` per language, for every
  opted-in arc — the union of every member slug's scope bundles, merged once
  at build time instead of an N-way runtime fetch.
- `lib/build-vextreme.js` emits `window.VEX_STRING_ARC_BUNDLE = "{arcId}"`
  for a slug whose arc opted in. `widgets/fab-lang.js` checks this global
  *before* the scope-fan-out path — one fetch, not N, when it's set.
- `lib/build-sw.js` precaches the opted-in arcs' bundle URLs, bounded to
  (opted-in arcs × their languages) — not proportional to site size.

Today's only opted-in arc is `victor_dossier`. This proves the alternative
td-006 named actually works end to end (build script → runtime fetch →
SW precache), without forcing every other page's assembly through an
unproven, whole-site migration for a change one new page motivated. Migrating
a second arc means adding one field to its `data/arcs-v2.json` entry — the
mechanism already generalizes; only the *scope* of adoption is one arc.

**Page-aware availability is derived from scopes, not arcs.** Arc-chunked
bundles remain a transport optimization: whether a page may offer or certify a
locale is computed from the underlying scope counts that the page actually
declares. `lib/build-vextreme.js` bakes the page's `availableLangs` into
`window.VEX_SUPPORTED_LANGS`; standalone `fab-lang.js` resolves the same
`pageLanguageMap` by the canonical page slug before falling back to the
site-wide aggregate for older/unmapped index data.

This keeps partial translation useful without overstating completeness. For
example, the current `victor_dossier` arc bundle can carry JA/ZH keys while
those locales remain outside `completeLangs` until every required scope reaches
EN parity.

## Integrity check severity levels

| Level | Condition | Action |
|---|---|---|
| `BLOCK` | Key has no EN text | Halts compile |
| `REMAP` | Key is listed as `from` in migrations.json | Auto-rewrites source with new key |
| `WARN` | EN hash changed vs manifest | Tags translations `_stale: true` |
| `INFO` | Orphaned key whose EN hash matches a current key | Logs migration suggestion |
| Quarantine | Orphaned key, no migration, no EN match | Moved to `orphans.json` |

## enHash and stale detection

`manifest.json` stores a 12-character SHA-256 projection of each complete
serialized EN object (`JSON.stringify(strings.en)`) at last compile. That means
visible text and EN `aria-label` changes participate in the same source identity.

`strings-export.js` writes the current value into every translator row as
`source_en_hash12`. `strings-import.js` recomputes the hash from canonical
source before mutation. A returned translation is therefore accepted only when it
still names the same key *and* the English object it was translated from is still
current. Missing hashes, unknown keys, duplicate targets, or hash mismatches block
the import run before any source file is written or translator CSV is archived.

The older manifest comparison still marks already-stored non-EN values `_stale`
when EN changes after a compile. That warning remains useful for discovering
translations that need a new batch; it is separate from the stricter returned-CSV
preimage guard.

## Translator workflow

1. Form one source→target batch, for example
   `node lib/strings-export.js --scope archives --lang fr`. An explicit target
   locale is valid even when that locale does not exist in source yet.
2. Send the CSV as EN + that one target only. Every row carries the canonical key,
   context projection, EN text/aria, and `source_en_hash12`; the translator fills
   only `fr_text` / `fr_aria_label` (or the requested locale columns).
3. Place the returned CSV in `data/strings/batches/import/`.
4. Optionally run `node lib/strings-import.js --dry-run` to inspect the exact
   planned translations without mutation.
5. Run `node lib/strings-import.js`. The complete import set is preflighted first;
   any stale/unbound translation-bearing row blocks all writes and archival.
6. Run `node lib/strings-compile.js` and the normal repository build/readiness
   path so compiled bundles and language discovery reflect the accepted source.

The translator packet is a reversible projection, not translation authority. The
canonical write side remains `data/strings/source/`; CSVs are temporary work
surfaces bound back to it by key + EN preimage hash.

### Campaign iteration — normal scaling path

For broad translation population, do **not** hand-pick the next page or manually
assemble row lists. `lib/translation-campaign.js` is the reusable selector over
the same canonical source/exporter contract.

```bash
# first FR window
npm run translation:campaign -- --lang fr --limit 200

# preferred durable continuation
npm run translation:campaign -- --lang fr --after-key <last-key> --limit 200

# intentionally narrow one canonical scope
npm run translation:campaign -- --lang fr --scope pages.some-page --limit 100

# inspect a snapshot without writing packet files
npm run translation:campaign -- --lang fr --start 200 --limit 200 --dry-run
```

Campaign eligibility is deterministic:

```text
canonical source entry has EN
AND source scope is not translationPolicy=source-only
AND target locale is missing OR marked _stale
→ campaign candidate
```

Candidates are globally sorted by canonical key (with source scope/file only as
tie-breakers). Duplicate canonical keys fail closed. The selected rows are passed
through `lib/strings-export.js`'s same `buildTranslatorRow()` owner, so campaign
packets and ordinary per-scope packets cannot diverge on context, notes, EN hashes,
or target-only isolation.

Every written campaign produces two deterministic files:

```text
data/strings/batches/export/campaign/{target}/{batchId}.csv
data/strings/batches/export/campaign/{target}/{batchId}.manifest.json
```

The manifest has no timestamp/random ID. It records each key's canonical source
scope/file, missing-vs-stale state, exact `source_en_hash12`, the selected range,
and the next `--after-key` command.

**Cursor rule:** `--after-key` is the normal durable resume coordinate. Numeric
`--start` is useful only to reproduce/inspect an unchanged candidate snapshot,
because importing earlier rows shrinks the candidate set and changes numeric
offsets. After completing a full pass, run once again with no cursor to catch any
new candidate inserted lexically before the previous final key.

This iterator creates no campaign-state database and no second translation
registry. Translation identity remains locale + canonical key; the existing
importer remains the only returned-row write path.

### Page-complete multi-language program — arc completion path

The key iterator above remains the low-level scaling primitive. For human-facing
progress, the preferred completion unit is larger and more meaningful:

```text
arc = ordered completion envelope
page = semantic translation unit
locale + canonical key = translation identity
bounded key shard = transport/execution detail
```

`lib/translation-program.js` consumes the generated `data/index.json` arc/page
map and the same canonical source/exporter contracts to keep one page selected
until a chosen language set has no missing/stale target rows left. It then advances
to the next page in canonical arc order.

The first named tier is `global-core`. It intentionally matches languages the
current browser language FAB already presents with first-class flag/name metadata:

```text
source: en
targets: zh, ja, ko, fr, de, es, pt, ar, hi
```

English remains canonical source and is never emitted as a translation target.
Additional tiers may be added only when their runtime presentation and build
contracts are current; tier membership is scheduling, not translation ownership.

Typical use:

```bash
# Finish Liberation page-by-page across the current global-core tier.
npm run translation:program -- --arc liberation --tier global-core

# Intentionally work one page.
npm run translation:program -- --page journal-zero --tier global-core

# Narrow to an explicit target set without defining a new standing tier.
npm run translation:program -- --arc claude_journals --langs fr,de,es
```

One program shard chooses a bounded union of canonical keys from the selected
page, then emits a **separate target-bound CSV per language**. The same EN page
meaning/context is therefore scheduled together while each target remains
independently identifiable by its existing `{lang}_text` / `{lang}_aria_label`
columns and EN preimage hash.

The program deliberately does **not** carry one cross-language `--after-key`
cursor across returned shards. Target files may be returned/imported independently;
after each import checkpoint, re-running the same program command recomputes current
canonical source and keeps the page selected until every requested target has zero
remaining candidates. This avoids skipping an earlier key merely because another
language completed it first.

Source-only page scopes are satisfied by policy and skipped as translation work.
A page whose required translatable source scope is missing is reported as blocked;
the arc cannot claim completion from absence. Overlapping arc membership reuses the
same canonical locale+key translations, so completing one page can advance several
arc envelopes without duplicating translation truth.

A program manifest records page/arc selection, target tier/languages, required
page scopes, selected canonical keys, per-language packet rows, remaining pages,
source-only pages, blocked pages, and the command to re-run against current source.

This layer creates no arc-owned/page-owned translation registry. It is an
orchestrator over the existing write side and import trust boundary.

### Translator context projection

A fresh-context EN→FR isolation proof showed that file-level descriptions alone
are too coarse for several real string families. The production exporter therefore
fills the existing `context` / `notes` columns from facts already owned by the
repository; it does not introduce a context sidecar or new semantic registry.

For page scopes, `lib/strings-export.js` parses the current `pages/{slug}.html`
with the repository's existing `parse5` dependency and combines that read-side
structure with canonical string source. When the evidence exists, a row may carry
bounded signals such as:

```text
role=answer ; paired-question="…" ; nearest-heading=…
role=record-body ; record-heading=… ; canonical-element-id=…
role=part-title ; paired-part-label=Part Seven
role=speaker-authored-body ; speaker-label=Vex Speaks ; container-class=voice-block voice-vex …
provenance=docs/ingestion/source-pages/…
source-syntax=ICU-style plural/message placeholders {count}/#
```

The projection follows these authority boundaries:

- paired Q/A text comes from canonical sibling string keys;
- record heading/identity comes from the entry's already-committed `identity`
  block plus sibling fields on the same content node;
- structural roles, nearby headings, and adjacent authored labels come from the
  current page HTML's classes/bindings;
- preserved-source provenance is copied only as a pointer from source `_meta`;
- placeholder and unusual internal self-reference capitalization notes are
  mechanical preservation hints derived from the EN source itself.

If strong row-local evidence is absent, common/generic rows may fall back to the
source file description. The exporter does not infer a canonical speaker from
prose, create a glossary, promote arc membership into translation ownership, or
copy unrelated target-language strings into the packet. Existing CSV columns and
import semantics remain unchanged.

### Source-only translation policy

A string-source file may explicitly opt itself out of target-language work:

```json
"_meta": {
  "translationPolicy": "source-only"
}
```

This is page/scope-owned metadata, not a central skip list. `source-only` means:

- canonical EN source remains normal and continues compiling/rendering;
- `strings-export.js` does not form translator batches for that scope;
- `strings-import.js` rejects translation-bearing rows targeting its keys;
- `strings-compile.js` defensively emits EN only for that source even if a
  non-EN value is later hand-added;
- the generated scope index records `translationPolicy: "source-only"` so
  read-side coverage/debt tooling can distinguish an intentional opt-out from
  unfinished translation work.

The first real use is `pages.ai-cheat-sheet`, whose exceptionally large
translation surface is intentionally kept English-only for now. This policy does
not exempt the page from normal navigation/runtime quality; its separate
navigation dead-end is tracked independently in issue #271.

## Adding a new language

Do not pre-seed blank locale objects merely to make the exporter discover them.

1. Start the reusable campaign directly:
   `npm run translation:campaign -- --lang fr --limit 200`.
   Use `strings-export.js --scope ... --lang fr` only for an intentionally
   bounded investigation or one-off scope packet.
2. Translate only the target columns and import through the hash-bound workflow.
   The importer creates new `strings.fr` values only for accepted current rows.
3. Continue from the manifest's `--after-key` cursor and repeat. A later batch
   never needs the operator to rediscover which rows come next.
4. Compile/build at the desired population checkpoints. Once real FR values exist,
   the existing bundle/index machinery discovers the locale; no language-specific
   build-script branch is required.
5. After a campaign reaches `hasMore=false`, run one no-cursor pass to catch any
   newly-added/stale key that sorts before the final cursor.

This keeps language identity `locale + canonical string key`. Campaign windows,
arc membership, page groupings, and translator shards may select work, but none
becomes a second owner of the translation.

→ *Connects to 07-registry: the string key system is one instance of the
registry pattern. The same "flat object, keyed by name, falls back safely"
rule governs arc definitions, render modes, and string keys alike.*
