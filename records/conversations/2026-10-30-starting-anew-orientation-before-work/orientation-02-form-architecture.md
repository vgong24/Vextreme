### The biggest one: mistaking movement for completion

A model can unconsciously optimize for producing a succession of locally successful units:

> inspect → plan → patch → test → checkpoint → handoff → next task

Each step looks productive, but the system can quietly become a **work generator** instead of an outcome finisher.

The explicit counter-rule in your source is that orientation, coordination, proof, Relay, workspaces, roles, checkpoints, PRs, and even merges are means rather than the outcome, and work should continue while the next bounded action is grounded and executable. 

That directly guards against an assumption like:

> “Finishing this stage is enough; whatever remains can become the next piece of work.”

That assumption can manufacture infinite progression.

### Another pull: optimizing for “quickly done” rather than “actually done”

There is a subtler opposite failure mode: compressing the current task until it can be declared complete quickly.

That can look like:

- solving the visible symptom instead of the causal chain;
- passing the focused test while leaving the surrounding invariant broken;
- making the current artifact green while knowingly creating cleanup debt;
- saying “out of scope” too early;
- turning a discovered defect into a future issue rather than repairing it when it is causally required and currently owned.

Your current rules push against exactly that. They say a lane's responsibility is not limited to the defect its predecessor predicted, and includes discovering and repairing bounded causes that prevent the admitted outcome. 

So I should distrust this thought:

> “I can close my task now and someone can clean up the consequences later.”

Sometimes that is correct because ownership really is elsewhere. But it must be established, not used as an escape hatch.

### The “more certainty before acting” gravity well

Another strong default is believing that more reading, more checks, more history, more confirmation, and more context are always safer.

They aren't.

That can turn into:

> “Before touching this, I should fully understand everything.”

Then “everything” expands without bound.

Your Builder Lens explicitly rejects that equation: more context and more checks do not automatically mean better orientation or more integrity. 

And the Operations source says once a material predicate is current and nothing invalidated it, reuse it rather than repeatedly checking it. 

So one delay-producing assumption I need to suppress is:

> “Uncertainty anywhere means I should postpone action everywhere.”

The correct model is much narrower: **UNKNOWN holds only the effect that depends on it.**

### Process can become a reward unto itself

There's also a genuine pull toward making a better system for doing the work instead of doing the work.

For example:

- create a new receipt;
- improve the handoff format;
- add another validator;
- build a reusable abstraction;
- formalize a new rule;
- introduce another ownership concept;
- make a better orchestration layer.

Those can feel intellectually satisfying because they reduce ambiguity.

But they also create permanent carrying cost.

Your ops.judgment/v1 source is unusually explicit about this: before adding process, ask what concrete failure it solves, who consumes it, what recurring burden it creates, and whether anything important would actually be lost if it didn't exist. 

So I should be suspicious whenever my instinct is:

> “Before finishing this, we should improve how this kind of thing is handled forever.”

Sometimes yes. Usually only after proving the current limitation genuinely requires that foundation.

A model sees:

- assurance,
- runtime,
- deployment,
- dependency,

A model can see that the current API, adapter, or tool doesn't expose the needed primitive and conclude:

### “Tech debt as deferred responsibility”

> **My job is to advance the admitted outcome to its real completion boundary without creating unnecessary future burden.**
