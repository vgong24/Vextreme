VexArchitecture

Build complex systems without letting every layer become the owner of the same truth.

Come inside the codebase. Follow one request from human intention to pixels, and watch the architecture emerge from the questions each layer is actually allowed to answer.

Accepted stability point · public origin guide VexLife-Android · PR #209

Use this page to understand why the first stable VexArchitecture body took this shape. Current VexLife-Android source and tests own present behavior. PR #209 preserves the pressure, subtraction, and proof that earned this stability point. Diagrams and code blocks here are architectural teaching projections unless explicitly labeled as a source snapshot; linked current source owns byte-exact implementation. The companion Live Demonstration is the object/scope-by-scope wiring walk when you need every construction and runtime edge made visible.

VexArchitecture did not begin with a framework diagram. It emerged while a real Android application kept forcing semantic state, asynchronous work, persistence, provider truth, dependency construction, logging, convergence, and presentation to stop impersonating one another.

How to read this guide

The architecture has one core causal path — and several relationships that sit beside it

Construction/lifetime creates and reuses the live objects in the path. VexLogger observes facts across owners. Relay/convergence appears only when independently-owned truths must become new relationship truth. Forensics explains why the shape was earned. None of those are automatic next runtime stages.

01 · Start with the failure

Complexity becomes dangerous when several layers start answering the same question

A serious feature can involve semantic state, user intention, concurrency, cancellation, persistence, remote truth, lifecycle, dependency construction, navigation, logging, and presentation. The usual response is to add managers. The deeper failure is that those managers gradually compete to define what the system means.

                         “WHO OWNS THIS?”
                                │
          ┌─────────────────────┼─────────────────────┐
          ▼                     ▼                     ▼
   FeatureManager       ExecutionManager         Repository
          │                     │                     │
          ├──────────────┬──────┴──────┬─────────────┤
          ▼              ▼             ▼             ▼
      ViewModel       UI State       Logger      DI Container
          └──────────────┴──────┬──────┴─────────────┘
                                ▼
                    the same meaning leaks everywhere

What it feels like in a mature codebase

A new requirement arrives and nobody can say whether it belongs in the feature state holder, execution wrapper, repository, ViewModel, logger, dependency graph, or UI state. So the requirement gets represented in several places. Every representation is individually reasonable; together they become drift.

The turning question

The question that changed the architecture: What exact question are we trying to answer, and which existing owner already has enough truth to answer it?

02 · The discovery

One question. One rightful owner.

VexArchitecture became smaller as the questions became clearer. These are not framework tiers. They are responsibility boundaries discovered by asking what truth each layer can actually know.

Core causal path · sequential
Family · semantic meaning
What does this Control mean against the exact current State?
Family owns State, Control, the lawful Act, optional Effect, and outward Projection/DisplayState. Parameter is optional and earned when a Family-scoped semantic value needs to remain recognizable across relationships; it is not a wrapper for every Kotlin argument. An Act may admit immediate semantic State and may also carry an inert Begin of Effect + overlap Approach. When concrete realization is needed, the Family-scoped Act.Method specializes reusable VexMethod without giving up semantic ownership. act(...) remains pure.
Execution · active custody
What asynchronous work is actually alive right now?
VexExecution owns Job custody, overlap behavior, and cancellation. It invokes already-authored work; it does not decide feature meaning, define a domain's lawful Success/Failure vocabulary, or become history.
Store / provider · outside truth
What does independently-owned reality currently say?
A Store is a boundary to outside truth. That truth may be SharedPreferences, a remote service, filesystem, OS state, device media, GPS, or another process. Store does not automatically mean database. Its contracts return the smallest truthful provider/domain fact; they do not adopt VexMethod.Result merely because an operation can succeed or fail.
Projection / presentation · human meaning
How should semantic truth become an experience without turning UI technology into semantic authority?
Family-owned projection becomes concrete presentation meaning, then Android/Compose manifests it. Compose is a manifestation technology, not the semantic owner.
Supporting relationships · orthogonal / conditional
Dependency Factory · construction
Why does this live object exist, what must exist before it, and for how long is it reused?
Providers declare prerequisites. Factories traverse, memoize, detect cycles, and preserve lifetimes. Construction identity never becomes semantic identity.
Logger · chronology
What was accepted or observed, and in what order?
VexLogger receives facts after rightful owners know them. It does not predict navigation, duplicate active-work registries, or mint correlation identities just to narrate history.
Relay / convergence · relationship truth
What new relationship truth emerges from truths owned somewhere else?
Convergence composes independently-owned truths. It can request change through rightful Controls; it does not steal another Family's Effect or State.

The reusable rule: before adding a new architectural noun, name the question it alone can answer. If an existing owner already has the truth, add the relationship there instead.

04 · Walk one feature from intention to pixels

Dark Mode is small enough to see everything, but real enough to expose the hard parts

ThemeMode is the patient zero because it crosses semantics, persistence, concurrency, execution, observation, projection, and Compose without being large enough to hide architectural mistakes.

Semantic vocabulary · abridged from accepted source

sealed interface Parameter {
    data class Mode(val mode: ThemeMode) : Parameter
}

sealed interface Control {
    data class Select(val mode: Parameter.Mode) : Control
}

sealed interface Effect {
    data class Save(val mode: Parameter.Mode) : Effect
}

Same in-process Parameter instance — an earned ThemeMode mechanism

ThemeMode deliberately preserves the exact Parameter.Mode instance across Control, Effect, and the fully-bound Method. That referential identity is used by this concrete currentness fence; it is not a universal distributed identity rule and does not authorize a generic currentness-token framework.

The realization seam
Family.act() authors semantic consequence. Begin remains inert. activate() mechanically binds the live Family and a maintained RelationshipId when the overlap law requires one. A concrete Family Act.Method contains the real Store/provider and semantic Parameter and specializes reusable VexMethod. The Store returns only its smallest truthful provider fact. Success / Failure are lawful returns from invoke(); if invoke() escapes with a Throwable, the Family / Execution continuation forms Error. launchWith() transports the already-authored owner / Approach / RelationshipId into VexExecution, which owns Job custody and cancellation without acquiring feature meaning.

05 · When work becomes asynchronous

Execution keeps custody. It does not become the feature.

Once an accepted Act needs runtime work, VexExecution answers a narrower question: which Jobs are alive under this maintained semantic relationship?

When maintained identity actually exists

Independent work
→ no maintained RelationshipId

Earliest / Latest / Queued work
→ maintained relationship exists
→ RelationshipId is derived from:
   live Family
   + Control kind/name
   + optional typed ResourceId when genuinely distinguishing

ordinary Control payload
→ NOT identity

The question to ask

Does unfinished work need to be related to other unfinished work as Earliest, Latest, or Queued?

No  → do not mint maintained identity.
Yes → derive the smallest semantic coordinate that already distinguishes that relationship.

RelationshipId exists only when unfinished work must be maintained as one semantic/runtime relationship. The actual Job remains the runtime occurrence, and ordinary payload never becomes identity merely because it is present on the Control.

06 · When outside reality arrives late

The race is where the architecture stopped being a clean diagram and had to answer time

The semantic State could already be Dark while an older Light Store observation was still in flight. If the old observation were blindly admitted, outside timing would overwrite a newer accepted human choice.

synchronization registry

ThemeMode's exact settlement rule

Select(Parameter B) makes B the unsettled selection, admits semantic State immediately, and starts Save(B). A mismatching Store observation is held because it carries no revision proving it is newer than B. When B's exact Method realization terminates, ThemeMode settles only if the completed parameter is referentially the same instance (===) as the current unsettled selection. Ordinary Store observations then resume. This is ThemeMode-specific, not a generic currentness framework.

Select(Parameter B)
→ B becomes unsettled
→ semantic State admitted immediately
→ Save(B) runs

mismatching Store observation arrives while B unsettled
→ HOLD
→ Store carries no revision proving it is newer than B

terminal Method realization for B
→ success / Store failure / execution failure
→ settle only when completed parameter === unsettled B
→ ordinary Store observations resume
07 · From semantic truth to human experience

Presentation manifests truth. It does not become the truth owner.

ThemeMode does not hand a Boolean straight to Compose and call that architecture. The Family first interprets semantic State into a Family-owned DisplayState; concrete presentation meaning follows; Android/Compose then manifests that meaning.

Projection / presentation · human meaning

ThemeMode State
      ↓
ThemeModeFamily.DisplayState
      ↓
VexThemePresentation
      ↓
VexLifeTheme
      ↓
Compose / system bars receive manifestation meaning
      ↓
presentation arrival, when actually observed
      ↓
human experience

Why the boundary matters

Projection describes what presentation should manifest. It does not, by itself, prove what actually reached the human. A Switch, segmented control, menu, voice command, or future surface may all select ThemeMode without redefining ThemeMode.

Do not invent a generic FamilyRenderer, UiState, or ViewState merely because a concrete presentation boundary already exists. Add another layer only when it answers a different required question.

Supporting topology · construction and lifetime

Make the object graph readable without turning dependency injection into runtime meaning

This is not another stage in the runtime path. VexDependencyFactory answers a different question: which live objects exist, what prerequisites built them, and which lifetime owns/reuses them. Provider object identity is the construction coordinate; prerequisites are explicit source; one factory lifetime memoizes one value per provider.

Cross-cutting observation · chronology

Chronology is powerful when it is allowed to remain chronology

VexLogger sits beside the causal path and receives accepted or observed facts from many rightful owners. It answers what happened and in what order; it does not become a shadow State machine, a predicted-future store, or an execution registry.

Production facts

App opened
Control accepted
Button clicked
Save requested
Save succeeded / failed
Screen disappeared
Screen arrived
Dialog appeared
Song ended
next song selected
song started

Identity stays separate

RelationshipId → which maintained semantic relationship
Job            → which live runtime occurrence
VexLogger      → what happened historically

A backend success is not proof that the intended presentation arrived. Log facts from the layers that actually observe them; derive history from chronology before minting correlation machinery.

Conditional composition · Relay / convergence

Relationship truth can be new without becoming a new owner of its inputs

Relay is not a mandatory stage after Family or Execution. It exists when independently-owned current truths must be composed into new relationship truth. A convergence owner may request change through another Family's public Control/Port; it may not bypass that semantic owner and invoke a foreign Effect directly.

EventsRepository truth ──────┐
AttentionPreferences truth ──┼─→ EventsConvergenceRelay → relationship truth
UserProfile truth ────────────┘

ConversationRepository truth ─┐
ConversationLab truth ─────────┼─→ VexConversationHybridRelay → relationship truth
                              └─→ request change only through rightful Controls

VexLifeRelayGraph is only a session-level projection of which independently-owned Relay nodes exist. It does not construct, activate, or semantically own them. Convergence may compose truth; it may not appropriate the authority that created the truth.

08 · What reality made unnecessary

Each deletion happened because another owner could answer the question more truthfully

The rejected abstractions were reasonable responses to real pressure. They disappeared when their question was returned to a smaller existing owner.

09 · Use it on your own feature

Do not copy ThemeMode. Reuse the questions.

The architecture scales by preserving the reasoning posture, not by forcing every feature into the same class diagram. Parameter, maintained RelationshipId, Relay/convergence, richer projection, and other mechanisms appear only when their specific question is actually present.

  1. Name the semantic question in ordinary language.
  2. Find the smallest owner that already knows the exact current truth needed to answer it.
  3. Define State and Control only when there is real semantic meaning to preserve.
  4. If accepted meaning requests outside work, author an Effect; do not claim the Effect already happened.
  5. Ask whether active work needs a maintained RelationshipId. Ordinary payload does not become identity by default.
  6. Let Execution own actual Jobs and overlap behavior, not feature meaning.
  7. Let the Store/provider expose independently-owned outside truth.
  8. Interpret observations through the rightful semantic owner before changing State.
  9. Project semantic State outward before choosing a concrete presentation technology.
  10. Log accepted and observed facts where they become knowable; derive chronology before adding IDs.
  11. Construct objects explicitly at the lifetime that actually owns them.
  12. Before inventing a new architectural noun, ask what required correctness disappears if you delete it.

A useful architecture does not ask every layer to become smarter. It makes each layer honest about the question it owns.

VexArchitecture became smaller as responsibility became clearer. The reusable innovation is not a set of class names. It is the discipline of preserving meaning, custody, outside truth, construction, history, convergence, and presentation without letting them collapse into one another.

Take the questions. Pressure them with your real system. Keep only the architecture that reality earns.
